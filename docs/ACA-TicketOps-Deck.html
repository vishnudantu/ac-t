ACA TicketOps

Ticket Request → Approval → Allocation → Distribution → Reconciliation

Feature guide & DIY kit · November 2026

What this platform does

ACA TicketOps replaces fragmented spreadsheets, chat threads and paper records with one auditable system that carries a ticket request from intake to reconciliation. Every material change is logged with who, what, when and before/after values.

The one-line lifecycle

Request→ Approval→ Allocation→ Distribution→ Reconciliation

Who uses it

  • Request Desk staff — capture requests on behalf of members
  • Apex / approvers — review, approve, partially approve or reject
  • Quota controllers — set stakeholder allocations per match
  • Distribution officers — issue, hand over and track tickets
  • Super Admin — roles, integrations, deletes, configuration

What you get

  • One source of truth for every ticket
  • Role-based access — people only see what they're allowed to do
  • Live inventory, quota and availability at every step
  • Full audit trail and printable reports
  • Real-time revenue with GST broken out

1 · Request intake

Staff create a ticket request for a member. The form captures everything needed for an approver to decide without a phone call.

What you fill in

  • Requester — pick an existing person or create a new one (name, mobile, email, organisation)
  • Match — the fixture this request is for
  • Ticket type — Complimentary or Purchase (mandatory)
  • Source & priority — how it arrived, how urgent
  • Ticket lines — one or more categories, each with quantity and notes
Live availability. As you pick a category, the form shows remaining capacity, already-allocated count and quota remaining for that category — so you never over-request.

Two save modes

  • Save as draft — keeps it private, no approval yet
  • Submit request — enters the approval workflow immediately

Built-in safeguards

  • Duplicate validation — warns if a similar request exists for the same person, match and category; only authorised roles may proceed
  • Complimentary/Purchase capture — the request clearly identifies intent
  • Clarification chat — staff and approvers can exchange guidance right on the request

2 · Approval workflow

Submitted requests pass through sequential approval steps. Each match can have its own multi-step workflow; if none exists, a sensible one-step default is created automatically.

Approving — full, partial, reject, return

  • Approve (full) — approves all requested quantities
  • Partial — approve a smaller number per item (e.g. 30 of 50)
  • Reject — closes the request
  • Return for clarification — sends it back to the requester with remarks
Quota-aware approvals. You cannot approve more than the stakeholder's remaining quota for that category. The decision dialog shows remaining availability and quota left per category, so you decide in seconds.

Reapproval after edits

Editing an already-approved request sends it back through the approval chain and clears the previous totals, preserving history.

Super Admin oversight

Super Admins (and users with approvals:escalate) see and act on every pending step, not just their own assignments — so auto-created workflows never disappear from view.

3 · Inventory & ticket categories

Inventory pools hold the actual stock: which stand, block, gate and format the tickets belong to, with quantities and face values.

Every field is editable

  • Stand name, block, gate, row/seat ranges
  • Ticket format — physical, digital, both
  • Face value (GST-inclusive)
  • Total quantity (never below allocated/issued/void)

Purpose — three modes per pool

ModeMeaning
100% ComplimentaryAll tickets free; ACA records the nominal GST price
100% PurchaseAll tickets sold at face value
MixedEnter a complimentary quantity and a purchase quantity for the same pool

Pricing unit

  • Per seat — face value applies to each ticket
  • Per suite — face value applies to the whole suite box

Ticket categories

Add, edit and delete categories (VIP, Premium, General stands, Media, Player guest, etc.) from Ticket Inventory → Ticket categories. Categories are reused across matches.

4 · Quotas & stakeholder allocation

Quotas split a match's ticket stock across stakeholder groups. Each quota allocates a number of tickets per category — so an approver can't approve more than a stakeholder's share.

The 15 built-in ACA stakeholder groups

Apex, BCCI, TCM, ACA Districts, ACA Clubs, ACA International Players, VDCA, District Collector, Commissioner of Police, GVMC, ACA Staff, Disabled Cricketer, Stadium Obligation, Press/Media, Stadium Chairman. You can add, edit or delete any of these.

How to set up

  1. Quota Templates (sidebar) — reusable stakeholder groups; add/edit/delete
  2. Quotas → New quota — pick a match and a template, then allocate quantities per category
  3. Edit any allocation later; capacity is validated so a category's allocations can't exceed its inventory
Quotas and requests are linked. When you approve a request, the app checks the remaining quota for that category and refuses to exceed it. No over-allocation, no duplicate follow-ups.

5 · Allocation & distribution

Allocation (reserving stock)

  • After approval, allocation officers reserve approved stock against inventory and quota pools
  • Created as a draft; must be confirmed by a user with the confirm permission
  • Transactions are concurrency-safe — two officers can't allocate the same tickets

Distribution (handing tickets over)

  • Issuance — give tickets to recipients, physically or digitally
  • Custody & acknowledgement — who collected, when, signature/reference
  • Returns — tickets given back, with reason
  • Reconciliation — issued vs allocated vs returned all tracked
Why distribution matters. Approval decides who gets how many; allocation decides from which stock; distribution is handing them over and proving it happened. It's the last mile of the lifecycle.

6 · Reports, revenue & reconciliation

Reports & analytics

  • Live aggregates with a match filter
  • Export CSV (formula-injection guarded), Excel (styled), or print

Revenue dashboard

  • Live issued-ticket revenue split by complimentary and sale
  • Purchase revenue = actual face value × issued
  • Complimentary revenue = your configured nominal price (default ₹499) × issued — so a ₹15,000 complimentary ticket doesn't load a large GST burden onto ACA
  • 18% GST computed separately on each side, with a net-of-GST total
  • A pending pipeline banner shows approved-but-not-yet-issued tickets so zero states are explained

Reconciliation

One screen compares requested vs approved vs allocated vs issued vs remaining per match, with venue capacity shown prominently.

7 · Search, notifications & integrations

Global search

Press Ctrl/Cmd + K anywhere to search requests, requesters and matches by number, name, mobile, email or title.

Notifications

  • Email via SMTP — dependency-free Node client
  • SMS & WhatsApp via Twilio
  • All channels off by default; enable per-channel after configuring
  • Requesters notified after approval decisions
  • Send test button delivers a test to your own account
  • Every attempt logged to the Notifications delivery log

Integrations page

Configure SMTP, Twilio and District (Zomato) from the UI — secrets masked, env vars still work as fallback. District webhook runs dry-run until you enable live mode.

8 · Administration & security

Users & roles

  • Create users, assign global roles
  • Edit permissions per role; create custom roles
  • Activate/deactivate (deactivation revokes sessions)
  • Super-admin-only deletes, guarded when history exists

Account

  • Edit your own profile (name, designation, department, mobile)
  • Change password with current-password verification; all sessions revoked
  • Admin password resets revoke the target's sessions
  • 16→8 character minimum, no hardcoded credentials

Built-in protections

  • Database-backed, revocable sessions; permissions reloaded per request
  • Zod validation on every API boundary
  • Login and password-change rate limiting
  • Audit events for every material change

9 · Mobile experience

  • Bottom tab bar for core destinations (Home, Requests, Approvals, Profile)
  • Card layouts for tables on small screens — no horizontal scrolling
  • Icon-only search on phones; off-canvas navigation
  • Thumb-friendly approval cards and dialogs
Designed desktop-first with mobile tolerance — works on any phone, tablet or desktop without an app install.

DIY kit · Deploy in 6 steps

  1. Get the code — git clone <repo> then cd ac-tickets
  2. Install — npm ci and npx prisma generate
  3. Configure — copy .env.example to .env; set DATABASE_URL, JWT_SECRET (32+ chars), ADMIN_INITIAL_PASSWORD
  4. Migrate — npx prisma migrate deploy (baseline first if the DB came from db push)
  5. Seed — npm run db:seed for roles/permissions; insert quota templates with the templates-only SQL (don't run the full seed in production)
  6. Run — npm run build then node scripts/start-demo.cjs (local) or docker compose up -d --no-deps app (server)

Sign in as office@andhracricket.com with your configured admin password. Change it immediately in any shared environment.

DIY kit · A typical match day

  1. Create the match — or Replicate an existing one to copy stands/inventory
  2. Add categories & inventory pools — stands, gates, quantities, face values, purpose and pricing unit
  3. Set quotas — allocate per stakeholder per category
  4. Capture requests — staff submit with live availability
  5. Approve — full, partial, reject or return; quota caps enforced automatically
  6. Allocate & confirm — reserve approved stock
  7. Distribute — issue tickets, record custody and returns
  8. Reconcile & report — revenue with GST breakdown, exports, audit trail
Golden rule: never edit the database by hand for operational changes. Use the UI so every change is audited and counters stay correct.
